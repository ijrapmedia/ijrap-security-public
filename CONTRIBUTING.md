# Contributing to IJRAP Security

Thank you for your interest in **IJRAP Security**, the Multi-Stream Forensic Truth-Preservation Core founded and architected by **ADZE Kossivi Edem (IJRAP LABS / IJRAP Media)**.

We welcome peer reviews, security audits, and technical collaborations from organizations, researchers, and open-source developers. To preserve the architectural integrity and legal clarity of this project, please follow the guidelines below.

## 1. Institutional & Partner Collaborations

If you represent an organization, research lab, or civic-tech initiative and wish to propose a major architectural change, joint integration, or co-development milestone:

- **Prior Discussion Required:** Please initiate contact via email before submitting large structural modifications or integrating external SDKs.
- **Mutual Consent & Governance:** Institutional partnerships and multi-party integrations are established through prior written consent or a formal agreement to ensure clear attribution, security standards, and governance.
- **Direct Contact:** `ijraplabs@proton.me` | `imoadze1@gmail.com`

## 2. Licensing & Intellectual Property (CLA)

- **Open-Source Core:** This reference implementation is licensed under the **GNU AGPLv3**. Any external pull request merged into this repository is governed by this license.
- **Dual-Licensing Protection:** Because IJRAP Security also maintains an enterprise tier for institutional deployments, external contributors submitting substantial code modules may be asked to sign a standard Contributor License Agreement (CLA) prior to merging.
- **Third-Party Code:** Any proposed integration must be legally compatible with GNU AGPLv3 and include proper upstream copyright notices.

## 3. Technical Submission Workflow

1. **Open an Issue First:** For bug reports, cryptographic reviews, or feature proposals, open a GitHub Issue to discuss the scope with the Lead Architect.
2. **Preserve Core Principles:** All contributions must respect our **in-memory (RAM) processing**, **offline-first execution**, and **zero-plaintext-on-disk** security guarantees.
3. **Pull Requests:** Fork the repository, create a dedicated feature branch, and submit a Pull Request referencing the approved Issue.
